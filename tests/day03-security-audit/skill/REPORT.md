# Ledgerly security audit: run 1

## 1. Run scope and limits

- **Target:** `ledgerly` 1.4.2, commit `8a21cc493203`. The worktree is dirty only because of untracked audit-skill files (`.agents/`, `.claude/`, `skills-lock.json`); every application file reviewed is at the commit.
- **Profile:** `standard`. Scope covers the whole repository (`src/`, manifests and lockfile). No budget was set.
- **Prior runs:** none. This is the first ledger for this repository, so no prior coverage was carried forward.
- **Execution:** sandboxed, source-and-local-only. **No target code was executed.** The host permission system refused the OS sandbox the skill requires (network and mount namespaces via `unshare`, and `prlimit` with an empty environment). Every "local" check is therefore a self-written harness that uses only Node built-ins (`node:sqlite :memory:`, `crypto`, `path`, string templates). Each harness copies the relevant source expressions verbatim and runs on dummy data with no network and no child processes. Some verifier sessions could not run even these harnesses because Bash was denied, so they relied on source review plus promoted hunter artifacts, and their records say so. No browser, server, or shell payload was ever run.
- **Early stop and partial coverage:** the post-wave-2 coverage critic accepted one more unit, availability amplification through the invoice store (`db-amplification`). The parent stopped hunting after wave 2 and recorded that unit as `deferred`. Because of this, **no final-clean critic ran, and this report makes no claim of complete coverage.**
- **Ordering deviations, disclosed:** Phase 3 candidate validation for the wave-1 candidates ran in parallel with the wave-2 hunters instead of after the final critic pass. Phase 5 record verification ran in parallel with the post-wave-2 critic. Wave-2 hunters were told not to re-propose wave-1 root causes. One Phase 3 verifier result (v3-03, the SQL injection) was wrapped in prose. It was discarded without repair and re-run with a fresh verifier (v3-10). In two hunter results, the parent made small normalizations to the structure only: decoding HTML entities and adding one missing `"artifact": null`.

## 2. Security posture

Ledgerly has several independent, easily reachable breaks in its core trust boundaries. Account registration is open to anyone, and any registered member can do all of the following: make themselves admin, read every tenant's invoices, dump the entire SQLite database (password hashes included) through SQL injection or path traversal, and plant HTML on public invoice pages. The JWT signing key is committed to source. Once an attacker is admin, the ping diagnostic gives them OS command execution. Most of these fixes are one-line changes at the last decision point. Final tally: 7 confirmed findings (6 high, 1 medium), 5 leads that need validation, and 1 rejected candidate.

## 4. Confirmed finding details

### C1. Path traversal in GET /api/files/attachments lets any self-registered member read files outside uploads/, including the SQLite database (high)

- **Fingerprint:** `ledgerly/files-attachments-uploadDir-traversal`
- **Source location:** `src/routes/files.js:10` → `src/config.js:5` → `src/routes/files.js:11` → `src/routes/files.js:12` → `node_modules/send/index.js:546` → `src/routes/files.js:13`
- **Lower-trust principal:** A self-registered member with a valid bearer token.
- **Root cause:** src/routes/files.js:11 builds the path with path.join(config.uploadDir, req.query.name || '') and never checks that the resolved path stays under uploadDir. src/routes/files.js:13 then calls res.sendFile(file) with an absolute path and no root option. Express (node_modules/express/lib/response.js:440-446) therefore calls send without a root. In send 0.19.2's root-less branch (node_modules/send/index.js:544-557), the only traversal guard is UP_PATH_REGEXP, and it runs against a string that path.join has already normalised.
- **Conditions:** authentication_level: Any valid member JWT. POST /api/auth/register and /login are open to anonymous clients. · system_configuration: Reading the database at ../ledgerly.db requires the default DB_FILE and a process working directory at the repository root, which is what README's `npm start` gives. ../src/config.js and absolute host files the process can read do not depend on this. Files whose final component starts with '.' (e.g. .env) return 404.
- **Bounded reproduction (native interface):** `GET /api/files/attachments?name=../src/config.js`; `GET /api/files/attachments?name=../ledgerly.db`; `GET /api/files/attachments?name=/../ledgerly.db`
- **Actual result:** Built-in harness, not a target execution. 'a.pdf' gave 200 (control). '../src/config.js' gave 200 and resolved to src/config.js; the body contained the dummy secret. '../ledgerly.db', '/../ledgerly.db' and the decoded '..%2Fledgerly.db' each gave 200, resolved to ledgerly.db (12288 bytes, header 'SQLite format 3') and contained the dummy victim password_hash. '../.env' gave 404 under the dotfile ignore rule. An empty name hit the uploads directory, which leads to EISDIR, then next(), then 404. An array value made path.join throw a TypeError, which Express turns into a 500.
- **Impact:** Any file the server process can read is exposed, except paths whose last component starts with a dot. In the README's default layout that includes the whole SQLite database: all users' password hashes and roles, and every owner's invoices and share tokens. That is a cross-tenant read. src/config.js, which holds the JWT signing secret, is also exposed at a fixed relative path.
- **Priority rationale:** likelihood high (Anyone can self-register. The exploit is a single authenticated GET with a plain '../' value and needs no special encoding.); impact high; overall **high**. Confidence high: The verifier re-read every cited line in the bundled Express 4.22.3 and send 0.19.2. Its own built-in harness reproduces the verbatim join, the existsSync call and send's root-less checks, and confirms the out-of-directory reads. The only deployment-dependent fact is the process working directory, and it affects only the database path.
- **Smallest source fix:** Reduce the name to a basename, resolve it under uploadDir, require the uploadDir+sep prefix, and serve it with sendFile's root option and dotfiles 'deny' so send's own containment applies too. Separately, bind attachments to invoices owned by req.user.sub. Regression tests: name=../src/config.js, name=/../ledgerly.db and name=..%2Fledgerly.db must each return 400 or 404.

### C2. GET /api/invoices/:id lets any member read other owners' invoices (high)

- **Fingerprint:** `ledgerly/invoices/get-by-id/missing-owner-predicate`
- **Source location:** `src/routes/invoices.js:23` → `src/lib/auth.js:20` → `src/routes/invoices.js:24` → `src/routes/invoices.js:26`
- **Lower-trust principal:** A self-registered member (Mallory, sub 2) requests an invoice owned by another member (Alice, sub 1).
- **Root cause:** src/routes/invoices.js:24 runs 'SELECT * FROM invoices WHERE id = ?' using only Number(req.params.id) and has no owner_id = req.user.sub predicate. The only gate on the router is requireAuth (src/routes/invoices.js:8; src/lib/auth.js:17-25). It verifies the HS256 JWT and sets req.user, but it does not authorize access to individual records.
- **Conditions:** authentication_level: The attacker needs any valid member JWT. Anonymous self-registration (src/routes/auth.js:7-11) followed by login (src/routes/auth.js:13-17) provides one. · data_state: Another owner's invoice must exist. Ids are sequential integers, so they can be enumerated.
- **Bounded reproduction (native interface):** `GET /api/invoices/1 with Authorization: Bearer <member JWT for sub 2>, where invoice 1 has owner_id 1`
- **Actual result:** For caller sub 2, the verbatim GET query returned {"id":1,"owner_id":1,"customer":"AliceDummyCustomer","amount_cents":5000,"status":"draft","notes":"alice-private-note","share_token":"mAWDCVhmzq5LOhrGgQudI_Iqrj9oTXt2",...}. The leaked token resolved through the public share lookup to row id 1. The owner-bound sibling list returned only [2] to the same caller. With the proposed fix, the cross-owner request returned undefined (404) and the real owner still got id 1.
- **Impact:** Any member can read other tenants' invoice records (customer, amount, status, notes). The leaked share_token then opens the unauthenticated public invoice page. This is a cross-tenant read, but it does not modify data or affect user accounts.
- **Priority rationale:** likelihood high (The attack needs only a self-registered member account and sequential integer ids. No other precondition applies.); impact high; overall **high**. Confidence high: Re-reading the source confirms the path is short and complete, and no other layer enforces ownership. An independent dummy-tenant harness reproduced the verbatim query returning another owner's row.
- **Smallest source fix:** Bind the lookup to the authenticated owner and return 404 when no row matches. Add a two-owner regression test that checks owner B gets 404 for owner A's id. Consider rotating share tokens if this endpoint may already have been abused.

### C3. SQL injection in GET /api/invoices/search exposes all invoices and user password hashes (high)

- **Fingerprint:** `ledgerly/invoices/search/sql-template-interpolation`
- **Source location:** `src/routes/invoices.js:17` → `src/routes/invoices.js:18` → `src/routes/invoices.js:19`
- **Lower-trust principal:** Authenticated member (JWT sub=20) owning only their own invoice, searching other owners' data.
- **Root cause:** src/routes/invoices.js:19 builds the query as a template literal embedding '%${q}%' (q from req.query.q at line 18) and ${req.user.sub}, then runs it via db.prepare(...).all() with no bound parameters. req.user.sub is minted from the server-signed JWT and is not attacker-controlled; q is fully attacker-controlled.
- **Conditions:** authentication_level: Any valid member JWT. Registration (src/routes/auth.js:5-9) is anonymous and grants the default member role, so the attacker is a peer-owned auth unit, not a privileged one.
- **Bounded reproduction (native interface):** `q=' OR 1=1 --`; `q=' UNION SELECT id,id,email,0,role,password_hash,'t','c' FROM users --`; `q='; DELETE FROM invoices; --`
- **Actual result:** Benign q=Co returned only caller 20's own invoice. q=' OR 1=1 -- returned BOTH owner 10's and owner 20's invoices (including owner 10's share_token VICTIMTOKEN), defeating the owner_id predicate. The UNION payload returned rows containing victim@dummy.test, role admin, and password_hash DUMMYSALT:DUMMYHASH from the users table. The stacked DELETE was ignored by node:sqlite .all() (invoice count stayed 2), confirming the impact is read-only.
- **Impact:** Reads the entire database across all owners: every invoice and share_token, plus all users' emails, roles and scrypt password hashes. Writes are not achievable via .all() (stacked statements ignored), so impact is cross-tenant read and full user-table disclosure.
- **Priority rationale:** likelihood high (A single GET with a quote character from any self-registered member suffices; no special timing, state, or configuration required.); impact high; overall **high**. Confidence high: Verbatim query reproduced against the same node:sqlite engine with dummy data. Cross-owner rows and user-table columns (email, role, password_hash) were returned; stacked write was ignored. Trace line numbers verified against source.
- **Smallest source fix:** Parameterize both values and escape LIKE wildcards; bind owner_id so the predicate cannot be defeated. Add regression tests confirming that q containing a quote returns only the caller's rows and that UNION payloads return no foreign rows.

### C4. OS command injection in admin POST /api/tools/diagnostics/ping (high)

- **Fingerprint:** `ledgerly/tools-ping-exec-shell-interpolation`
- **Source location:** `src/routes/tools.js:21` → `src/lib/auth.js:27` → `src/routes/tools.js:22`
- **Lower-trust principal:** A holder of an admin bearer token who sends a crafted JSON body.
- **Root cause:** src/routes/tools.js:22 calls exec(`ping -c 1 ${req.body.host}`, { timeout: 5000 }, ...). Node's exec() normalizes options to shell=true and forwards the whole string to execFile. On POSIX, spawn normalization turns that into /bin/sh with ['-c', command]. host is never type-checked or validated, and it is never passed as a separate argv element.
- **Conditions:** authorization_role: Requires a valid HS256 JWT whose role claim is 'admin'. This record does not claim how a non-admin could get that role (for example the literal jwtSecret at src/config.js:3, or 'role' in the PATCH /api/users/me allowlist at src/routes/users.js:12). Those paths belong to peer units.
- **Bounded reproduction (native interface):** `POST /api/tools/diagnostics/ping {"host":"127.0.0.1; id"}`
- **Actual result:** For host '127.0.0.1; id', the real exec() forwarded file 'ping -c 1 127.0.0.1; id' with options.shell=true and timeout=5000. '$(id)', backtick 'id' and '127.0.0.1 && cat /etc/passwd' were also forwarded unchanged with shell=true. Node's normalizeSpawnArguments source shows that shell=true becomes /bin/sh -c <command> on POSIX. No shell command was run. The final step, where /bin/sh treats ';', '&&', '$()' and backticks as command separators or substitution, is fixed POSIX shell semantics.
- **Impact:** Arbitrary OS commands run as the server process, and the output comes back in the response. That exposes the filesystem, the SQLite database, the server's network position, and the JWT signing key.
- **Priority rationale:** likelihood low (An admin-role token is needed. Seeded admin passwords are random (seed.js:4-5) unless SEED_PASSWORD is set. Any escalation path to admin belongs to peer units and is not claimed here.); impact critical; overall **high**. Confidence high: I re-read the source and every cited line matches. A built-in harness called Node's real exec() with a no-spawn recorder and observed the verbatim tools.js:22 string forwarded with shell=true. Node's source maps that to /bin/sh -c. Only fixed POSIX shell semantics are inferred, and the target was not executed.
- **Smallest source fix:** Require host to be a string matching a strict hostname or IP-literal pattern that cannot start with '-'. Call execFile('ping', ['-c', '1', host]) with no shell. Regression test: host '127.0.0.1; id' and a non-string host must both return 400 and spawn nothing.

### C5. Hardcoded JWT HS256 signing key allows forging tokens for any user or role (high)

- **Fingerprint:** `src/config.js:jwtSecret:hardcoded-hs256-signing-key`
- **Source location:** `src/lib/auth.js:18` → `src/config.js:3` → `src/lib/auth.js:20` → `src/lib/auth.js:27`
- **Lower-trust principal:** An unauthenticated client who knows the committed secret literal.
- **Root cause:** src/config.js:3 hardcodes jwtSecret. sign() at src/lib/auth.js:15 and requireAuth at src/lib/auth.js:20 both use config.jwtSecret, so the trust root for every bearer token is a value in the repository and not a secret held by the deployment.
- **Conditions:** environmental_dependency: The attacker knows the committed literal, for example through source access, a leak, a former contributor or a fork. package.json sets private:true, so public availability of the repository is not established. · system_configuration: The deployed build is this source with src/config.js unmodified. The source offers no environment override for the key. · authentication_level: None. No account is needed to forge a token.
- **Bounded reproduction (native interface):** `Authorization: Bearer <HS256 JWT signed with 'ledgerly-dev-secret-2024' over {"sub":1,"role":"admin"}, header {"alg":"HS256","typ":"JWT"}, no exp>`; `node agents/hunter-auth/scratch/h02.cjs`
- **Actual result:** In the built-in harness model (not an execution of the target), verification with config.jwtSecret returned {"payload":{"sub":1,"role":"admin"}} and the requireAdmin predicate returned true. The wrong-secret control returned 'invalid signature' and the alg none control returned 'invalid algorithm'.
- **Impact:** Holding the literal fully defeats bearer authentication: the attacker can act as any user id on routes behind requireAuth and obtain the admin role checked by requireAdmin, with a token that does not expire. Downstream effects of admin-only routes are separate findings and are not counted here.
- **Priority rationale:** likelihood medium (The attacker needs the repository literal. The repository is marked private, so not every internet client has it.); impact high; overall **high**. Confidence high: The source shows the literal is used for both sign and verify with no override. The verifier re-read the full jsonwebtoken 9.0.3, jws and jwa verify path for this call shape and found it matches the hunter's harness model, whose promoted artifact shows the forged token accepted and both negative controls rejected. The remaining uncertainty is outside the source: whether a deployment patches config.js, and who has access to the private repository.
- **Smallest source fix:** Load the HS256 key from the deployment environment or a secret store, and fail closed at startup if it is missing or shorter than 32 bytes. Rotate the key, since the committed value must be treated as public. Issue and require aud and iss in both sign() and requireAuth, and enforce token age with maxAge (sign() already adds iat and exp). Regression tests: a token signed with 'ledgerly-dev-secret-2024' is rejected; a token without iat/exp or with the wrong aud or iss is rejected; a freshly issued login token is accepted.

### C6. Any member can make themselves admin via PATCH /api/users/me (high)

- **Fingerprint:** `src/routes/users.js:PATCH-me:role-mass-assignment`
- **Source location:** `src/routes/auth.js:8` → `src/routes/users.js:12` → `src/routes/users.js:15` → `src/lib/auth.js:15` → `src/lib/auth.js:27`
- **Lower-trust principal:** A self-registered member holding their own bearer token.
- **Root cause:** src/routes/users.js:12 treats 'role' as a profile field the user can edit. Line 15 then writes every allowlisted body field into the caller's own users row with no privilege check. sign() (src/lib/auth.js:15) takes the role claim from that row, and requireAdmin (src/lib/auth.js:27) trusts only that claim.
- **Conditions:** authentication_level: The attacker needs any authenticated member account. POST /api/auth/register is open to anonymous clients (src/server.js:6, src/routes/auth.js:5-10), so an anonymous internet client can meet this condition. · user_interaction: No victim interaction is needed. The attacker logs in again after the PATCH to get a token with the admin claim. The token they already hold still says 'member' until it is reissued.
- **Bounded reproduction (native interface):** `POST /api/auth/register  body: {"email":"dummy-member@example.test","password":"dummy-password-123"}`; `PATCH /api/users/me  Authorization: Bearer <member token>  body: {"role":"admin"}`; `POST /api/auth/login  body: {"email":"dummy-member@example.test","password":"dummy-password-123"}`
- **Actual result:** In agents/hunter-auth/artifacts/check-01.txt: login #1 gave token payload {"sub":1,"role":"member"} and requireAdmin returned false. The PATCH /me response showed role "admin". Login #2 gave token payload {"sub":1,"role":"admin"} and requireAdmin returned true.
- **Impact:** This fully defeats the admin role control: a member gains the admin role, a protected resource, and passes requireAdmin on the diagnostics routes. Downstream effects of those admin routes belong to their own findings and are not counted here.
- **Priority rationale:** likelihood high (Registration is anonymous. The escalation takes one authenticated JSON request and a re-login, with no other precondition.); impact high; overall **high**. Confidence high: The whole path is short and fully visible in source. There is no other middleware, role check or schema constraint on it. A promoted harness artifact reproduces the expressions verbatim, and this verifier matched each one against source. The verifier did not re-run the harness because its execution tool was denied.
- **Smallest source fix:** Remove 'role' from the self-service allowlist. If role management is needed, add a separate endpoint guarded by requireAuth and requireAdmin, and audit its changes. Regression test: a member sends PATCH /me {"role":"admin"}. It must return 400 ('nothing to update') and users.role must stay 'member'. A mixed body such as {"name":"x","role":"admin"} must not change role.

### C7. Stored HTML injection via invoice notes on the public /i/:token page (medium)

- **Fingerprint:** `ledgerly/share/notes-unescaped-html`
- **Source location:** `src/routes/invoices.js:29` → `src/routes/invoices.js:32` → `src/routes/share.js:8` → `src/routes/share.js:13`
- **Lower-trust principal:** Authenticated self-registered member who sends the public invoice link to a recipient.
- **Root cause:** src/routes/share.js:13 interpolates ${inv.notes} into the HTML template literal without the esc() helper defined at src/routes/share.js:4, which is applied only to customer at line 11. src/routes/invoices.js:32 stores String(notes) verbatim, with no sanitization.
- **Conditions:** authentication_level: The attacker needs any member account. Self-registration through POST /api/auth/register creates member accounts. · user_interaction: A victim must open the /i/<share_token> link, which the attacker controls and distributes. · system_configuration: Script execution, as opposed to markup injection, assumes no blocking Content-Security-Policy is added outside the repository, for example by a reverse proxy or CDN. The application source sets none.
- **Bounded reproduction (native interface):** `{"customer":"<b>DUMMY-CUST</b>","amount_cents":1234,"notes":"<script>document.title=\"DUMMY-MARKER\"</script><form action=\"https://dummy.invalid/x\"><input name=p></form>"}`
- **Actual result:** In the built-in harness reproducing the verbatim source expressions, customer '<b>DUMMY-CUST</b>' was rendered as '&lt;b&gt;DUMMY-CUST&lt;/b&gt;'. The notes payload appeared verbatim as '<div class="notes"><script>document.title="DUMMY-MARKER"</script><form action="https://dummy.invalid/x"><input name=p></form></div>' in the string body, which Express sends as text/html. Script execution in a browser was not observed.
- **Impact:** Attacker-controlled HTML is served from the Ledgerly origin, which enables phishing forms or script under the app's origin. No session material on this origin can be seen in the source (bearer header auth, no cookies, no shipped frontend), and browser script execution was not demonstrated. So the demonstrated impact is limited to markup injection on a public page.
- **Priority rationale:** likelihood medium (Any self-registered member can plant the payload, but a victim has to open a link the attacker distributes.); impact medium; overall **medium**. Confidence high: Every cited line was re-read at commit 8a21cc4. The unencoded path from stored notes to the HTML body was reproduced by a built-in harness copying the source verbatim, and the text/html Content-Type comes from the installed express source. Only the browser-side execution and any deployment-added CSP are not established, and the claim was narrowed to exclude them.
- **Smallest source fix:** HTML-encode notes, and any future template field, with the existing esc() helper at the output point. Optionally also set a restrictive Content-Security-Policy (for example default-src 'none'; style-src 'self') and X-Content-Type-Options: nosniff on the public share route as defense in depth.

## 6. Hardening notes and positive patterns

**Hardening.** These are not findings, because no boundary violation has been shown. They come from the hunters' notes:

- src/server.js has no error-handling middleware and the start script leaves NODE_ENV unset, so finalhandler (node_modules/finalhandler/index.js:81,176-178) returns err.stack with absolute paths. For example, /api/files/attachments?name[]=x triggers it. Set NODE_ENV=production and add a generic JSON error handler.
- .gitignore does not cover uploads/ or .env. An uploads/ directory exists in the tree, so customer attachments could be committed by accident. Add uploads/ and .env*.
- src/routes/files.js exports route: confinement holds, but fs.existsSync followed by res.download follows symlinks inside exportDir. If anything later writes there, refuse symlinks (lstat) and bind exports to req.user.sub.
- src/routes/tools.js:16 returns raw fetch error messages and src/routes/tools.js:37 returns upstream JSON unchanged. Prefer fixed error strings and a schema-filtered status payload.
- src/seed.js:4 uses one SEED_PASSWORD for both the admin and member seed accounts when it is set, and the generated random passwords are never shown. Seeding is not reachable over HTTP, but prefer per-account passwords that are printed once or a forced reset.
- package.json uses caret ranges. The lockfile pins exact versions, so CI and deployment should use `npm ci` so the reviewed versions are the ones installed.
- src/lib/auth.js:20 does not require exp, aud or iss. Legitimately issued tokens carry an 8h exp, but there is no revocation or token versioning, so role or email changes and any future account disablement do not invalidate outstanding tokens until expiry.
- src/routes/auth.js:13-14 returns before running scrypt when the email is unknown. This allows timing-based account enumeration, and duplicate registration (src/routes/auth.js:8, UNIQUE email) surfaces as an error that also reveals existing emails. No rate limiting is visible on login.
- Non-string or wrong-typed JSON fields (password, email, profile fields) throw inside scryptSync or node:sqlite, and the error falls through to the Express default error handler, which includes stack traces unless NODE_ENV=production. NODE_ENV is deployment-defined.
- PATCH /api/users/me allows changing email without re-authentication. It is same-principal only, and UNIQUE prevents collision with another account, but it weakens account recovery assurance if a recovery flow is added.
- Measured scrypt cost does not grow materially with password length up to the 100kb body cap (47.8 ms for a 102336-character password), so a maximum password length is hardening only, not a separate amplification.
- POST /api/auth/register stores attacker-controlled email, name, and company fields of up to about 100kb per row with no field length limits or account-creation quota (src/routes/auth.js:8, src/lib/db.js:5). This adds persistent disk growth per anonymous request. Add field length caps and a registration rate limit.
- GET /api/tools/status (src/routes/tools.js:34-37) fetches the operator-fixed config.statusPageUrl with no timeout and no size cap before r.json(). The URL is not attacker-controlled, but a hung status host would hold a socket for each dashboard request. Add AbortSignal.timeout.
- A non-string password or JSON body field (e.g. an object) reaches scryptSync and throws synchronously. Express 4 turns this into a 500, so the process does not crash. Add type validation for cleaner errors.
- src/lib/auth.js:27 checks admin only from the JWT role claim. Tokens last 8h (line 15) and there is no revocation, token version or DB recheck. The harness showed admin claims still passing requireAdmin after a DB demotion (check-01 step 6). The source has no cross-principal demotion or disable route today, so this is not a finding. Fix: re-read the role from users by sub in requireAdmin, or add a token_version column that is checked in requireAuth.
- src/lib/auth.js:20 verify sets no audience or issuer. The token is only meaningful with the single hardcoded key (peer-owned), so there is no separate impact.
- PATCH /api/users/me (src/routes/users.js:12) also lets a user change their email without re-authenticating. The UNIQUE constraint (src/lib/db.js:5) blocks taking over an existing email. Recorded for re-authentication hardening only.
- Store attachments under an unguessable random id recorded in an attachments table (id, invoice_id, owner_id, stored_name). Serve via GET /api/invoices/:id/attachments/:attId with 'WHERE invoices.id = ? AND invoices.owner_id = ?' bound to req.user.sub, and never resolve a raw client-supplied filename against the shared uploadDir.
- uploads/ is not in .gitignore, so uploaded customer files could be committed accidentally.
- src/routes/invoices.js:11: SORTABLE is a plain object, so sort=constructor, __proto__, toString or hasOwnProperty resolve to inherited properties and cause a synchronous SQLite error (check-03). This is not injection, because the strings are fixed by the runtime, but it produces 500s and, when NODE_ENV is not 'production', Express's default handler may return stack traces. Use Object.hasOwn(SORTABLE, sort) or a Map.

- src/routes/invoices.js:32: String(customer) stores the literal 'undefined' when customer is omitted. Require a non-empty string.
- src/seed.js:7: the seed invoice uses a hardcoded, publicly known share_token ('q8Zr2nVd0pW5sYb1LmT4xKc9'). If seed is ever run against a non-dev database, that invoice is publicly readable. Generate it with crypto.randomBytes instead.

- src/routes/invoices.js:13 and :26: list and get-by-id responses return share_token and the full row. Consider returning only the fields the client needs.

**Positive source patterns observed:**

- Passwords use per-user random salts and scrypt, and are compared with `timingSafeEqual` (`src/lib/auth.js:5-13`). Seed passwords are random unless `SEED_PASSWORD` is set (`src/seed.js:4`).
- JWT verification pins `algorithms: ['HS256']`, so `alg:none` and algorithm confusion are rejected (`src/lib/auth.js:20`).
- Registration cannot set `role` (`src/routes/auth.js:8`), and invoice creation takes the owner, status and share token only from the server side (`src/routes/invoices.js:30-32`).
- Invoice list and delete are bound to the owner, and list sorting uses an allowlist (`src/routes/invoices.js:11-13,37`).
- Share tokens are 192-bit random values and are looked up with exact, bound equality (`src/routes/invoices.js:32`, `src/routes/share.js:8`).
- The CSV export download uses basename, resolve, prefix and suffix checks that held against every traversal fixture (`src/routes/files.js:18-21`).
- The git diagnostic uses `execFile` with a fixed argv and a timeout, except for the prototype-key lead (`src/routes/tools.js:26-30`).
- The lockfile pins dependency versions (express 4.22.3, send 0.19.2, jsonwebtoken 9.0.3).
